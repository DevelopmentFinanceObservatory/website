# Analytics and error monitoring

Usage events go to our own database, to Cloud Logging and to PostHog, errors to Sentry, and page views to Google Analytics on production, behind the cookie banner.

## Usage events

The events DFO Overview asks for (Data access → "Events to record") land in the `event` table (`db/schema.ts`, migration `0006_events`): one row per event with a dotted `name`, the event's own `props` (JSONB), `user_id` when signed in, a random per-browser `visitor_id` (localStorage, no cookie) when the visitor has consented, and the `page`. No event row holds an IP address or the text of a Studio prompt. The search events hold the first 500 characters of the query.

The browser stores `visitor_id` only after the visitor accepts "DFO usage statistics" in the Analytics category of the cookie banner (Usercentrics service `L3eMCSMT3WELG7`, read through the CMP's `window.__ucCmp` API and `UC_CONSENT` event in `src/lib/consent.ts`). Until then, including while the banner is loading or blocked, events arrive with a null visitor id. Withdrawing consent deletes the stored id.

The server sets a second cookie, `dfo_v`, for rate limiting. It holds a random id with an expiry and a signature, is HttpOnly, `SameSite=Lax` and lasts 24 hours, and it is set or renewed on a page request (`src/proxy.ts`, `src/lib/proxy/visitor.ts`). Any client that loads a page gets one. It lets the proxy count a reader's API calls apart from other readers behind the same address (`docs/design/api-keys.md`, "The visitor tier"), which makes it strictly necessary to run the service, so it is set without consent. It is never joined to `visitor_id`: no event, log line or export table carries it or a digest of it.

Every event also carries `internal_eng`, a boolean written by `track()` when the event is recorded: true when the signed-in user's verified email is on the `INTERNAL_ENG_EMAILS` list (comma-separated entries, each an email address or a bare domain such as `example.org`, matched exactly, case-insensitively). Unset or empty means false for every event, and a list change reaches new events only. A signed-out visitor is always false. A prop the browser sends under that name is overwritten. The export keeps it on every event, so a query can leave out engineering traffic. Rows exported before `internal_eng` existed lack the key, so a query treats a missing key as false (`COALESCE`). The anonymous events (`share.open`, `embed.view`, `data.view`, `feedback.submit`) never record a user id, so their `signed_in` always reads false, even when `viewer` is `owner`. On them `internal_eng` matches the domain entries of the list only (`anonymousWho()` in `src/lib/events/internalEng.ts` passes on the email's domain alone), so a single-address entry cannot make the flag name one person. A session read on these events and on `POST /api/events` that fails or takes over 500 ms (`boundedLookup()` in `src/lib/events/boundedLookup.ts`) records the event as signed out, except on `share.open` and `embed.view`, which record it as `viewer: unknown`.

`share.open` and `embed.view` carry `viewer`, who opened the share, from `shareViewEvent()` in `src/lib/events/shareView.ts`:

- `owner`: a signed-in viewer who made the share, from the viewer's `share_token` row.
- `other`: a signed-in viewer who did not make it. A guest's share has no maker account, so every signed-in view of it is `other`.
- `signed_out`: the session read answered with no session.
- `unknown`: the session read or the owner read failed or took over 500 ms, so the viewer may be the owner.

Opens by people other than the maker are the `other` and `signed_out` rows.

Every search post, the base run and each edit after it, ends on one terminal event: `search.query`, `search.empty`, `search.edit`, `search.error`, or a `superseded`, `reset` or `left` abandon. A page closed mid-post leaves only its `hidden` abandon. `useSearchRun` gives each post a tracker from `searchPostTracker()` in `src/lib/search/searchEvents.ts`, which sends only the first terminal event it is asked for. These run fields are on every one of them:

- `searchId`: a UUID minted when a search starts (a query, a permalink, a share or version link), kept by its edit posts.
- `post`: 0 for the base run, then 1, 2, … for each edit post of the same search.
- `source`: where the search came from: `typed`, `example` (a suggestion or example chip), `catalogue` (the starting point), `refine`, `retry`, `permalink` (a shared or bookmarked `?q=` link), `share` (`/s/<id>`) or `version_link` (`?spec=`). A search typed or picked on the homepage reaches `/data` with `?q=` and keeps `typed` or `example`.
- `edited` (true from post 1) and `editKind` (`slot`, `entity`, `window`, `facet`, `pick`, `measure`, `parsed`, `shared`, or `replay` for a permalink's stored edits).
- `traceId`: the engine's trace id, the `trace_id` on the dfo-apis `resolve` log line, null when the post ended before the engine answered.
- `ms`: client time from the post's start to the event.
- `hidden`: true when the page was hidden while the post was in flight.

A settled post adds `outcome` (a resolution's `status`, `definite` / `candidates` / `no_data` / `unsupported` / `mixed`, else `catalogue` or `declined`), `engineMs` (the engine's `done.elapsed_ms`), `byStep` (the engine's per-step timings) and `timedOut` (the engine's soft deadline cut the run short).

A post sends `search.abandon` with reason `hidden` the first time the page is hidden while it is in flight. Background tabs keep streaming, so the post usually settles later, with `hidden: true`. A post still in flight when the reader goes to another page of the site ends on a `left` abandon, and its stream is aborted. A true abandon, a page closed with the post in flight, is a `hidden` abandon with no terminal event for the same `(searchId, post)`: no settle, no error, and no `superseded`, `reset` or `left` abandon. The tracker sends `hidden` only before the post ends, so any such event came after it:

```sql
select a.props->>'searchId', a.props->>'post' from event a
where a.name = 'search.abandon' and a.props->>'reason' = 'hidden'
  and not exists (
    select 1 from event t
    where (t.name in ('search.query', 'search.empty', 'search.edit', 'search.error')
           or (t.name = 'search.abandon' and t.props->>'reason' <> 'hidden'))
      and t.props->>'searchId' = a.props->>'searchId' and t.props->>'post' = a.props->>'post');
```

Browser code calls `track()` from `src/lib/events/client.ts`, which posts to `POST /api/events` (only the names in `BROWSER_EVENT_NAMES` in `src/lib/events/browserEvents.ts`, so server events are refused; props capped at 8 KB; 204 for an event taken); server code calls `track()` from `src/lib/events/track.ts` directly. Every event name lives in `track.ts`, and the names browser code may send also go in `BROWSER_EVENT_NAMES` in `src/lib/events/browserEvents.ts`. Add a name there first.

When `POSTHOG_KEY` and `POSTHOG_HOST` are set, `track()` also forwards each event server-side to PostHog (EU cloud) through `sendEventToPosthog()` in `src/lib/events/posthog.ts`. The event keeps its props, minus any key starting with `$`, and adds `environment`, `page`, `signed_in` and `country`. Its `distinct_id` is the visitor id for a consented visitor, else the account id for a signed-in one. An event with neither gets a fresh random UUID and `$process_person_profile: false`, so PostHog creates no person for it. Each event carries the browser request's `User-Agent` as `$raw_user_agent`, which PostHog's bot filter reads. `country` is the two-letter code Cloudflare puts in the `CF-IPCountry` header, or null when Cloudflare has no location (`XX`) or the visitor uses Tor (`T1`). Every event sets `$geoip_disable: true`, because PostHog would otherwise place it at the Cloud Run server, and no event carries the visitor's IP. All six server callers pass the browser request's headers: `POST /api/events`, feedback, shares (Studio and search), share page loads, embed renders and the sign-in callback. An event with no request behind it passes `headers: null` and carries no user agent and a null `country`.

`track()` also writes each event as one JSON line on stdout, through `logEvent()` in `src/lib/events/eventLog.ts`, before the database insert and the PostHog forward, so the line exists whether either of them fails. Cloud Logging stores it as a structured entry with `jsonPayload.message = "event"`: `{severity: "INFO", message: "event", name, props, page, signedIn}`. Its `page` is the path alone, with any query string or fragment dropped, as on the request log line; the table and PostHog keep `page` as sent. The line holds the event's full props, including the clipped query text of the search events, and keeps it as long as the log bucket's retention. It holds no `userId` and no `visitorId`: `signedIn` says only whether a user was signed in. A search event's `traceId` prop is the `trace_id` on the dfo-apis `resolve` log line, so the two join on it in SQL once the log bucket is linked to BigQuery.

A resolved part records what the question asked for, and counts the StatVars and places it expanded to: an aid query expands to hundreds of each, which would pass the 8 KB cap. A role asked for as a named group, such as the European Union, records the group, three of its members and the member count. A set-valued filter with more than three refs records three and the count. `sources` lists every source id while the whole event fits the cap, and the first three per part when it does not; `sourceCount` is always the full number, so a list shorter than the count is a sample. The run and settle fields stay on every form, and the floor drops only `byStep`. If the event still exceeds the cap, each resolved part keeps only `measure`, `statVarCount`, `entityCount`, `sourceCount` and the per-role place `count`, and the event carries `truncated: true`. If that form is still too large, the event ends on a fixed-size floor: an empty `query`, no refused parts, and per resolved part only the integer counts; `specIds` and `measures` stay on every form. The ladder runs on the complete props, `seeds` included, and measures the JSON length as the route does; the API's limit of six parts bounds the floor.

In production the `dfo-prod-website-export` Cloud Run Job (`db/export-events.ts`) copies the table every hour into the BigQuery table `event` in the `website_export` dataset, one partition per UTC day of `created_at`. Each run replaces every day from the latest loaded day minus one through today, plus any earlier day whose row count differs from its partition's, so a day that failed to load is retried until it matches, plus every day holding a row whose `export_rules` digest differs from the current one, so a change to the export rules or the hashing key reaches every partition already loaded. The copy hashes `visitor_id`, `user_id` and the `shareId` prop, keeps `page` only as a site path without its query string and with share ids written `:id`, and keeps only the props `PROP_RULES` in `db/event-export.ts` allows, so it holds no search text. `deploy/README.md` ("Event export") has the schema. Questions about the text itself stay in Postgres, e.g. the most-requested measures:

```sql
select r->'measure' as measure, count(*) from event, jsonb_array_elements(props->'resolved') r
where name = 'search.query' group by 1 order by 2 desc limit 20;
```

The same Job, after the event days load, copies the Postgres view `account_daily` (`db/account-export.ts`) into the BigQuery table `account_daily` in the same dataset, replacing the whole table in one load job, so a failed run leaves the previous table. The view counts new accounts per UTC day and organisation, as `day`, `organisation` and `accounts`, from the first account's day through yesterday, so every day it holds is complete. An organisation is the lower-cased email domain once the domain holds at least 3 accounts, counting the accounts created through yesterday; `Personal email` for a webmail domain, whatever its count; and `Other organisations` for any other domain, so a domain with fewer than 3 accounts never shows by name. A day without new accounts is one row with a null `organisation` and 0 `accounts`. The table holds no email address and no user id.

The Job also copies the Postgres view `account_organisation` into the BigQuery table `account_organisation`, one row per account counted in `account_daily`, replacing the whole table each run. A row holds `user_hash` and `organisation`, and no creation day. Both views leave out accounts being deleted (`user.deleting_at` set). `user_hash` is the digest the event export writes as `user_hash` on the account's events, so a query joins an account's events to its organisation, for example to count the organisations with regular users. `organisation` is the account's label in `account_daily`, so no domain below 3 accounts shows by name. The table holds no email address and no user id. It carries no engineering flag, so filter the joined events on `internal_eng`, as every other query does. `deploy/README.md` ("Accounts") has the schemas.

The Job also copies the Postgres view `conversation_export` into the BigQuery table `conversation`, replacing the whole table each run. A row holds `id_sha256`, `agent_session_sha256`, `user_hash` (the same digest as above, so a query joins the conversation to its owner's events) and `created_at`, for each saved conversation of an account not being deleted. `id_sha256` and `agent_session_sha256` are the lower-case hex SHA-256 of the conversation id and of the agent session id, used to join Langfuse sessions: `to_hex(sha256(session_id)) = agent_session_sha256`. The harness session id is a bearer credential and the conversation id can equal it, so the view digests both and the raw ids are neither readable by the export role nor exported. `agent_session_sha256` is null before a conversation's first turn. The table holds no title, transcript or widgets.

## Sentry

`@sentry/nextjs` on both sides: `instrumentation-client.ts` (browser), `sentry.server.config.ts` / `sentry.edge.config.ts` loaded from `src/instrumentation.ts`, `src/app/global-error.tsx` for a crash in the root layout. Everything is off without `NEXT_PUBLIC_SENTRY_DSN`. `sendDefaultPii` is false and there is no session replay, so it needs no cookie consent.

Browser reports go through `POST /api/monitoring`, our own same-origin tunnel (past ad blockers). It is our route rather than the plugin's `tunnelRoute` rewrite because a rewrite forwards request headers, and behind HTTP Basic auth the browser's `Authorization` header makes Sentry reject every envelope with 400.

Source maps upload during `next build` when `SENTRY_ORG`, `SENTRY_PROJECT` and `SENTRY_AUTH_TOKEN` are set; without them the build just skips the upload.

## Google Analytics

`src/components/atoms/GoogleAnalytics/GoogleAnalytics.tsx` loads GA4 (measurement ID `G-NCWQ8XTXG1`) from the root layout when the page is served from `developmentfinance.org` or `www.developmentfinance.org`. The check reads the host name because dev and production build the same Dockerfile with the same build-time variables. The ID and the host list are constants at the top of that file.

Consent Mode v2 runs in advanced mode. An inline script in `src/app/layout.tsx` sets every consent type to `denied` on every host, ahead of the Usercentrics loader, and GA sends cookieless pings until the visitor chooses. Usercentrics has Google Consent Mode on and a "Google Analytics 4" service, and sends the `consent update` when the visitor chooses.

Embeds load neither Usercentrics nor GA. On an `/embed/` path (`isEmbedPath()` in `src/lib/embed.ts`) the root layout's inline loader skips injecting the Usercentrics script and `GoogleAnalytics` renders nothing, because a banner would cover the card and iframe storage is partitioned per host site, so a reader would be asked again on every partner site. The server counts each embed render as `embed.view` instead, with a `data.view` for the DFO data it shows, and each share page load as `share.open`, both with no visitor id, no user id and nothing stored on the device. `embed.view` holds no address. `data.view` stores the caller digest in the events table and the export keeps it, so the two rows of one render sit next to each other in the export. The count is iframe loads, including crawlers that render a host page and direct opens of the embed URL. `host` keeps only the hostname of the `Referer` and is null when the host page's referrer policy strips it.

The "Privacy settings" button in the footer (`src/components/organisms/Footer/Footer.tsx`) calls `showPrivacySettings()` from `src/lib/consent.ts`, which opens the Usercentrics settings layer so a visitor can change either choice after the first banner.

Enhanced measurement records page views on App Router navigations (history changes), outbound clicks, scrolls, site search (`?q=`) and file downloads, so the site sends GA only its config call. The `track()` events above go to our own database, Cloud Logging and PostHog; GA receives none of them.

To check it on production, open the network panel and filter on `google-analytics.com/g/collect`. Before consent the requests carry `gcs=G100`, and after accepting in the banner they carry `gcs=G111`. The visit then shows in GA under Reports → Realtime. Localhost and dev make no `gtag/js` request.

## Request log

The site writes one JSON line to stdout for each logged request, which Cloud Logging stores as a structured entry. `src/instrumentation.ts` registers `registerRequestLogging()` in `src/lib/proxy/requestLog.ts` at server startup. It subscribes to Node's `http.server.request.start` diagnostic channel, reads each request's target there, and attaches one `close` listener to each response it logs. A static asset gets no listener. Node emits `close` after `finish`, so every request writes exactly one line, when its response closes, with `finished` true for a response that ended normally. A response that closes before it ends, such as a page render the visitor abandons, an aborted RSC fetch or an `/mcp` event stream the client closes, writes its line then, with the status code it had sent. A request accepted before the subscription starts has no listener, so its line is written when its response finishes. Visitor counts come from this line, because Cloud Run's own request log records Cloudflare's edge address as the client.

```json
{
    "severity": "INFO",
    "message": "request",
    "caller": "ip:3f9c0a…",
    "method": "GET",
    "path": "/embed/abc123",
    "host": "developmentfinance.org",
    "kind": "page",
    "status": 200,
    "finished": true,
    "bot": false,
    "agent": "browser",
    "agent_name": null,
    "prerender": false,
    "tier": null
}
```

`tier` is whose rate-limit count a call spent, `key`, `visitor` or `address`, read from the response's `x-dfo-limit-tier` header, which the server removes before the response leaves it, and null for a call nothing counted. `visitor` means a valid `dfo_v` cookie counted the call; the line holds the tier and never the visitor id. `caller` is the same `ip:<digest>` the `/mcp` proxy sends upstream as `x-dfo-caller` (`src/lib/proxy/caller.ts`): an HMAC of the client address (an IPv6 address as its /64) under `CALLER_HMAC_KEY`, with the address taken from `X-Forwarded-For` at the `TRUSTED_PROXY_HOPS` position. It is null when the key is unset or the request carries no usable address. `path` is the request target as it arrived, captured when the request starts so a later rewrite does not change it. It has no query string or fragment, and dot segments are resolved, so `/a/../mcp` is logged as `/mcp`. A target such as `//mcp` is read as a path and logged as `//mcp`. An http or https absolute-form target such as `http://host/path` is logged as its pathname. Any other target, such as one with another scheme (`ftp://`, `file:`, `mailto:`), an authority-form `host:port`, or an http or https URL that does not parse, is logged as the fixed path `/:unparsable`, since it can hold a user name, a password or an IP address. The asterisk-form target of `OPTIONS *` is logged as `*`, with kind `page`. `kind` is `api` for `/api`, `/mcp`, `/openapi.json` and `/codes` and every path below each of them (`/apiary` is not one). That covers the site's own endpoints under `/api`, such as auth, events and share, as well as the platform proxy's routes. `kind` is `prefetch` for a Next.js prefetch (`Next-Router-Prefetch`) or a browser prefetch (`Sec-Purpose: prefetch`), `rsc` for a client-side navigation (`RSC: 1`) and `page` for everything else. A `Sec-Purpose` header does not change the kind of an RSC fetch or a Next.js prefetch. Embeds under `/embed/` are logged as pages. `/_next/` files, images and fonts are not logged, and are dropped before the line's headers are read or its caller computed. `status` is the response's HTTP status code. `finished` is true when the response ended normally and false when it closed first, so a status of 200 with `finished` false is a visitor who left a stream. A response that closes before the app sent a status has none of its own, so the line carries 499 (client closed request) with `finished` false. The 499 means the app sent no status before the connection closed. It also covers a response Node answered itself, such as a 408 on a request timeout or a 400 on a client error, which never passes through the app. A response that called `writeHead` but wrote nothing to the socket before the close is logged with that status and `finished` false. Infra's parse keeps the line and counts it as a 4xx, outside the readers' 2xx count. Infra's `website_requests_daily` counts a line whose response did not finish like a finished one. `prerender` is true for a document request (no `RSC` and no `Next-Router-Prefetch` header) with `Sec-Purpose: prefetch;prerender`: the browser renders the page ahead of time and shows it on activation with no second request, so that one line is the page view. It has kind `page`, which keeps infra's `website_requests_daily` counting it as a parsed page request. The line is a page view whether or not the visitor opens the page, because the server cannot see activation. `agent` says what sent the request (`requestAgent()` in `src/lib/bot.ts`). It is `sdk` for any request with a non-empty `X-DFO-Client` label after cleaning, which the DFO SDKs send. A missing or blank `User-Agent` gives `none`. Any other request takes its value from a table of named user agents: `crawler` for GPTBot, OAI-SearchBot, ClaudeBot, Claude-SearchBot, PerplexityBot, Googlebot and bingbot; `user_fetcher` for ChatGPT-User, Claude-User and Perplexity-User, which fetch a page for one person's question to an assistant; `sdk` for dfo-python and dfo-ts; `mcp_client` for codex-mcp-client, openai-mcp, claude-code and Antigravity. Any other user agent is `other_bot` when the `isbot` package flags it (link previews such as Slack's, headless browsers, HTTP libraries, tools such as curl) and `browser` when it does not. On `/mcp` and the paths below it, a `user_fetcher` is an `mcp_client`, because Claude's connectors send Claude-User. An unnamed bot there stays `other_bot`, since an MCP SDK sends its HTTP library's user agent, as a scanner does. `agent_name` is the table's name for the agent, such as `GPTBot` or `dfo-python`, and null for an agent outside the table. An `sdk` request is named by its `X-DFO-Client` product token when that is `dfo-python` or `dfo-ts`. `bot` is the `isbot` verdict on the `User-Agent` header, independent of `agent`: true when the header is missing or empty, or when the `isbot` package flags it. Crawlers such as Googlebot, bingbot and ClaudeBot, link previews such as Slack's and Discord's, headless browsers and tools such as curl are bots. An SDK or MCP client can be a bot by this test when its user agent is an HTTP library's, so readers of the APIs filter on `agent`. Infra's `website_page_views_daily` uses `bot`, and `track()` drops every event whose user agent `isbot` flags. A client that sends a browser's user agent counts as a reader. The line holds no raw IP address, query string, cookie, `Authorization` header or user agent.

The line reads the request's raw headers, which keep the `RSC` and `Next-Router-Prefetch` headers that Next.js removes from `request.headers`. Logging leaves request bodies unread, so API and MCP payloads stream to their handlers in full. A Next.js proxy would buffer those bodies and truncate them at its default 10 MB limit.

### API key usage line

A call to the platform proxy on a surface that honours API keys (`/api/v1/*`, the Datasets API's routes below `/api/v1/datasets/` included, `/openapi.json` and `/codes`) that carries an API key also writes one line from `forward()` (`src/lib/proxy/forward.ts`), when the call is decided and before it goes upstream:

```json
{
    "severity": "INFO",
    "message": "api key call",
    "surface": "api",
    "outcome": "allowed",
    "keyId": "…",
    "accountId": "…"
}
```

`keyId` is the key's public id (the plugin's `apikey.id`) and `accountId` its owner. Neither is the key or its hash, which are never logged. `surface` is `api` or `datasets`. A key on `/mcp` or the Studio is stripped unread and writes no line. `outcome` is `allowed` (counted against the account), `limited` (a 429: the account's per-minute limit, its daily quota or the key's daily cap was spent, or the address's limit when the key was not yet looked up), `invalid` (unknown, disabled, expired or over-long: a 401, with null ids), `forged` (a key whose signed tag no server secret made: a 401 before any lookup or count, with null ids) or `unavailable` (the key store could not be read, so the call went on as anonymous, with null ids). The `request` line above names a keyed call by its address: it is written from the raw headers when the response closes and does not see the key. Count keyed use from this line.

## Studio prompt allowance

A Studio prompt is one turn (`POST /api/studio/turn`). The proxy atomically reserves one from the caller's daily allowance before it forwards the turn (`src/lib/studio/spendPrompt.ts`). Refused requests consume no allowance. A guest gets 5 a day per network address, an IPv6 address counted by its /64, so guests behind one shared address share them. A signed-in user gets 75 a day, counted per inbox: the address lower-cased, without a `+tag` and, for Gmail, without dots (`inboxOf` in `src/lib/auth/inbox.ts`). An email code makes a separate account for each spelling of one address, and those accounts share the 75. Both reset at 00:00 UTC. The numbers live in `src/lib/studio/promptAllowance.ts` and the counts in the `limit_counter` table. A turn past its allowance gets a 429 `resource_exhausted`, whose detail the chat shows as the reply. Allowance and rate-limit queries use a separate two-connection pool with a 400 ms database statement limit, a 500 ms client query limit, and a 2 s connection limit, so they cannot occupy the pool used for sessions and history. An allowance that cannot be read gets a 503. A turn the harness answers with anything but success gives its reservation back in its original counter window, since no model ran. The proxy forwards only the four routes the browser calls (`turn`, `interrupt`, `cancel`, `composition`) and answers 404 to any other path, so no encoding of a path reaches the turn route without spending a prompt.

The browser also counts a guest's prompts in localStorage and replaces the prompt with a sign-in wall at 5. Clearing it brings the prompt back but not the allowance. Guests get no history or saving (both need an account). A guest can make snapshot shares, up to 10 a day per network address (`GUEST_SHARES` in `src/lib/chat/shareMode.ts`). Those shares have no owner, so nobody can switch or remove them.

In local dev every guest comes from the same address and so shares one allowance. Sign in, or delete the `studio-guest:` rows from `limit_counter`.
